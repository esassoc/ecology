Header Nav

A batteries-included top app bar composed from the chrome bricks (esa-app-bar + esa-icon-link + esa-nav-dropdown): brand slot, data-driven primary nav with dropdowns, an actions slot, and a user menu. Disclosures are native details/summary, so it needs zero runtime JS. For full control, compose the bricks directly.

Stable .astro import EsaHeaderNav from '@esa/ecology/esa-header-nav.astro';

Preview

Open Reports or the avatar to expand the native disclosures.

States

Brand only, no signed-in user — the avatar / user menu is omitted when user is absent.

API

PropTypeDefaultDescription
items EsaHeaderNavItem[] [] Primary nav links. Each is { label; href?; icon?; children? }; an item with children renders a dropdown.
user EsaHeaderNavUser — Optional signed-in user { name; email?; avatarUrl?; initials? }. When present, renders the avatar + user menu.

Slots

PropTypeDefaultDescription
brand slot — Left-aligned logo / wordmark area.
actions slot — Right-aligned controls placed before the user menu (e.g. search, notifications).

Nav dropdowns and the user menu are native details/summary disclosures (via esa-nav-dropdown) — no JavaScript required.

Accessibility

  • Each item with children renders an esa-nav-dropdown disclosure; plain items render an esa-icon-link.
  • Disclosures are native details/summary — keyboard toggling and the expanded state come for free.
  • The avatar button carries an aria-label naming the user (User menu for …).
  • Decorative chevrons and glyph SVGs are aria-hidden.

Theming surface

Every public token this component reads, extracted from its source at build time, split by blast radius: the hooks that belong to this component, then the shared and system tokens it consumes alongside everything else. The Resolves to column walks each token's real lineage — component → semantic → primitive → raw value — so you can see exactly where re-pointing it lands. A spoke re-skins by overriding these in its theme-<slug>.css; component internals are never edited. No hook for what you need? File it with /request-lego.

Type roles it names

This component does not set a size, weight, face or tracking of its own — it names a composite, and the composite carries all five. A composite is a class rather than a token, so none of it appears in the tables below; re-theme text by re-pointing the token family, not by editing the component.

Tier 3's --focus-ring-width now reads this instead of holding a bare 2px, which is the same shape --focus-ring-color has always had (a thin tier-3 alias over a tier-2 role) — width was simply never given the tier-2 half. * * This role was rejected once, and the rejection is worth recording because its PREMISE was wrong rather than its reasoning. The argument against an `emphasis` width was that every 2px border in the kit is micro-geometry — spinner rings, the kbd keycap lip, a chevron. The focus ring was not in that enumeration and does not fit it: 33 components render it, more than read any other tier-3 token, and it is not micro-geometry but an accessibility affordance whose weight is a legitimate brand axis (a spoke that needs a heavier ring for contrast has to be able to reach it). It is also not a `border` in any component — every consumer paints it with `outline` or `box-shadow` — which is precisely why a survey of BORDERS missed it.
