Button Group

Groups buttons with connected borders. Use it purely for visual grouping, or as a radio-like segmented control that emits a composed change event.

Stable wc import '@esa/ecology/esa-button-group'; Angular usage

Preview

The group has no size of its own — set size on each child button, alongside its variant. The group only connects the borders.

Modes

selection-mode="none" is the default — buttons are visually connected but each acts independently.

selection-mode="single" turns the group into a segmented control. One child stays active; give each child a data-value and listen for the change event.

API

PropTypeDefaultDescription
selection-mode 'none' | 'single' 'none' 'none' is visual grouping only; 'single' acts as a radio-like segmented control with one active child. Property: `selectionMode`.
value string '' In 'single' mode, the data-value of the currently selected child.

Events

EventTypeDefaultDescription
change CustomEvent<{ value: string }> — Fired in 'single' mode when the active child changes. Composed and bubbling; detail.value is the selected child's data-value (falling back to its text content).
Binding these events from Angular

Every one of these is a CustomEvent, so the payload is on $event.detail — $event.target.value reads empty, with no error. The names are lowercase and Angular passes them to addEventListener verbatim, so camel-casing one means it never fires.

  • (change)="onChange($event.detail)"

Accessibility

  • The host sets role="group" automatically on connect.
  • In single mode the active child receives aria-pressed="true" and a data-selected attribute for styling; the rest get aria-pressed="false".
  • The change event is composed and bubbles, so it crosses shadow boundaries and can be caught on the host or an ancestor.
  • Slotted children remain real <button> elements — keyboard focus and activation come for free.

Theming surface

Every public token this component reads, extracted from its source at build time, split by blast radius: the hooks that belong to this component, then the shared and system tokens it consumes alongside everything else. The Resolves to column walks each token's real lineage — component → semantic → primitive → raw value — so you can see exactly where re-pointing it lands. A spoke re-skins by overriding these in its theme-<slug>.css; component internals are never edited. No hook for what you need? File it with /request-lego.

Type roles it names

This component does not set a size, weight, face or tracking of its own — it names a composite, and the composite carries all five. A composite is a class rather than a token, so none of it appears in the tables below; re-theme text by re-pointing the token family, not by editing the component.

The argument against an `emphasis` width was that every 2px border in the kit is micro-geometry — spinner rings, the kbd keycap lip, a chevron. The focus ring was not in that enumeration and does not fit it: 33 components render it, more than read any other tier-3 token, and it is not micro-geometry but an accessibility affordance whose weight is a legitimate brand axis (a spoke that needs a heavier ring for contrast has to be able to reach it). It is also not a `border` in any component — every consumer paints it with `outline` or `box-shadow` — which is precisely why a survey of BORDERS missed it.
