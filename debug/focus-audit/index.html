Focus audit

Five findings from reading every focus rule in the kit — 40 components plus packages/tokens/src/focus.css and a11y.css.

Findings 1, 2 and 5 were fixed on 2026-08-17 and are kept below because the measurements are still the reason. Findings 3 and 4 are still open and are what this page is now for — both were scoped out deliberately, with reasons recorded in docs/system-improvement-ledger.md. Delete this file once those two are triaged too.

FIXED 1 · The two-band ring was reverted. Three documents still described it.

Resolved 2026-08-17 by stripping, not by landing the halo. The contrast problem the halo existed for is now solved by a ramp walk: --color-border-default-focus takes the first step of the brand's own ramp that clears 3:1 on every surface. The hub moved one step, grass-9 → grass-10, 2.66:1 → 3.07:1. All halo references were rewritten to describe that, including two the original audit missed — three test comments in check-a11y.test.mjs, and the token table on /foundations/focus. The five-token table below is therefore historical: the probe now shows three declared tokens and two undeclared, which is the state that was fixed.

/foundations/focus tells you the ring is a brand band plus a near-black halo, lists five tokens, and publishes a house shape for component authors to copy. Three of those tokens exist. Two do not — not in tokens.css, not in component-tokens.css, not in the semantic JSON. Neither does the semantic role the table says the halo maps to.

Token the docs publishMaps toActually declared?Computed value on this page
--focus-ring-color --color-border-default-focus yes …
--focus-ring-width --border-width-focus yes …
--focus-ring-offset 2px literal yes …
--focus-ring-halo --color-border-default-focus-halo NO …
--focus-ring-halo-spread derived NO …

The last column is read at runtime with getComputedStyle on :root. An empty result means the property is not declared anywhere, so any var() reading it with no fallback drops the whole declaration.

Which is what the house shape the docs hand to authors does:

.thing:focus-visible {
  outline: var(--focus-ring-width) solid var(--focus-ring-color);
  outline-offset: var(--focus-ring-offset);
  box-shadow: 0 0 0 var(--focus-ring-halo-spread) var(--focus-ring-halo);  /* ← paints nothing */
}

The box-shadow line is invalid at computed-value time and is thrown away. It is not a wrong colour, it is no declaration — silently, with no console warning. The two live samples below are the shipped esa-button and a bare <button> ringed by focus.css. Tab into them: one band, not two.

Where the stale references live:

  • apps/site/src/pages/foundations/focus.astro — the token table (lines 10, 13), the prose at line 76, and the copyable house shape at line 89.
  • plugins/spoke-kit/skills/design-principles/SKILL.md:57 — this one ships to spokes. A spoke is told to re-point --focus-ring-halo; doing so does nothing, and the read sites carry fallbacks, so it fails silently.
  • plugins/spoke-kit/skills/accessibility/forced-colors.md:83 — inside a worked example.

The revert itself is intact: grep -rn 'focus-ring-halo' packages/ecology/src returns nothing, and the components kept the good half of that pass — every ring is now an outline rather than a box-shadow, which is what makes them survive forced-colors. Only the documents were left behind. The uncommitted diff is still sitting at focus-revert.patch in the repo root. Already logged in docs/system-improvement-ledger.md:51.

FIXED 2 · A focused error field painted two rings in two colours

Resolved 2026-08-17. All six error rules now re-point the TOKEN — .field--error { --focus-ring-color: var(--form-error-border-color) } — rather than overriding outline-color, so it is one red band, not a second one. The token form is what reaches the chip remove buttons too, which a property override on the container would have missed. (This paragraph and the err column said outline-color until 2026-08-19; no component ever declared that, so every line number in the column pointed at nothing.) The cells below now show a single red ring. This was originally an override (both rules used box-shadow); the 2026-08-16 forced-colors pass converted the base rule to outline and left the error rule behind, which is what split them into two bands. Error red is now gated at 3:1 on all four surfaces like the brand ring. And the colour-column split flagged below turned out to be the worse half of the finding: --color-border-utility-danger is red-6, a subtle border step at 1.40:1, so three of the six error rings were nearly invisible.

Click into the right-hand field. No keyboard needed — these use :focus-within, so a mouse click paints the ring.

Two separate problems in one table, and the second turned out to be the worse one. The doubling was the visible symptom. The colour column was the real defect: three components used --form-error-border-color and three used --color-border-utility-danger. I originally read that as "solid red vs a translucent fallback". It is worse than that — --color-border-utility-danger resolves to red-6 (#fdbdbe), a subtle border step, measuring 1.55:1 raised and 1.40:1 sunken against the 3:1 an indicator owes. So the token resolving correctly was not the safe case: three components shipped an error ring that was very nearly invisible, and nothing measured it because the ring had no gated row at all.

All six now read --form-error-border-color — red-9, 3.43:1 on the worst surface, and the same token --_field-border-color already uses, so the ring and the border are the same red by construction. Four fail rows now grade it. --color-border-utility-danger keeps its one correct reader: esa-error-summary's 1px panel border, which is what a step 6 is for.

P3 4 · Fifteen rings ignore --focus-ring-offset

A spoke re-pointing the token moves 43 rings and misses 15. Six of the misses are a deliberate inset written the long way; nine are plain drift.

Offset writtenRulesWhereRead
var(--focus-ring-offset) 39 the house shape — button, checkbox, radio, switch, tabs, dialogs, all six form fields, … correct
calc(var(--focus-ring-offset) * -1) 4 esa-entity-search.ts:491, esa-command-palette.ts:301, esa-combobox.ts:985, esa-search-panel.ts:356 correct — an inset ring still derived from the token
-2px (hardcoded) 6 esa-dropdown-menu.ts:188, esa-tab-layout.ts:223, esa-command-palette.ts:355, esa-combobox.ts:1147, esa-select.ts:1036, esa-filter-dropdown.ts:614 deliberate inset, wrong spelling — the row above expresses the same idea through the token
1px (hardcoded) 6 esa-select.ts:1010, esa-combobox.ts:1114, esa-input-tag.ts:678, esa-filter-pills.astro:142, esa-file-list.ts:218, esa-file-upload.ts:388 drift — all six are the small ✕ inside a chip or row; nothing documents 1px
2px (hardcoded) 3 esa-app-shell.astro:233, esa-app-shell.astro:248, esa-combobox.ts:891 drift — the token’s own value, written literally

Tab across this row — the gap between the button and its ring changes on the remove buttons. Both are shipped components at their real sizes.

The -2px insets are defensible: those six rows run edge-to-edge inside an overflow: hidden panel, so an outward ring would be clipped. The problem is that the kit already has a spelling for that — calc(var(--focus-ring-offset) * -1), used by esa-search-panel, esa-command-palette's search box, esa-combobox and esa-entity-search. Two spellings for one idea, in the same two files in two places (esa-combobox writes it both ways, at lines 985 and 1147).

FIXED 5 · esa-app-shell rang from a fill role

Lines 233 and 248 painted 2px solid var(--color-background-brand) — the solid fill role, not --focus-ring-color — and were the only two focus rules in the kit with no --focus-ring-width. Both are now the house shape.

This was filed as "nothing to see on screen", and the ramp walk is what made it real. The two tokens used to resolve identically, so the defect was invisible. Now --color-border-default-focus is grass-10 while --color-background-brand stays grass-9 — so those two rings would have been the only ones left in the kit at 2.66:1 on a sunken surface. The probe below is the proof: the two rows must now differ. That is also why 52 literal var(--focus-ring-color, #46a758) fallbacks across 34 components were retargeted to #3e9b4f — while the 39 var(--color-background-brand, #46a758) fallbacks were deliberately left alone, since the brand fill has not moved.

Checked and clear

  • The revert is complete in component code. No component references a halo token.
  • No component paints its ring with box-shadow alone. The ledger's "14 components" note describes the state before the same pass; all 14 now lead with outline, which is what survives forced-colors. check-a11y check 9 holds the line.
  • The :focus / :focus-visible / :focus-within split is consistent and matches what /foundations/focus documents: :focus-within on text-entry wrappers, bare :focus only in esa-error-summary, :focus-visible everywhere else.
  • No clipped rings found. Every rule inside an overflow: hidden or scrolling container already uses a negative or zero offset. If you saw a ring cut in half, tell me which component — I could not reproduce it by reading.
